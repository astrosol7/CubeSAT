MASTER PROMPT — AIRBORNE DISASTER-RESPONSE UNIT ELECTRONICS & PROTEUS CIRCUIT DESIGN

1. PROJECT CONTEXT

We are a team developing a small 2U CubeSat-form-factor airborne disaster-response prototype carried by a helium balloon.

Important clarification:

This is NOT an orbital CubeSat. The physical platform is a helium-balloon airborne unit used as a technology demonstrator for Earth observation, sensing, communication, and disaster-response support.

The project focuses on disaster response during/after an event, not disaster mitigation.

The four disaster scenarios we want the overall system to support are:

1. Wildfire/fire
2. Flood
3. Landslide
4. Earthquake

The system should use a combination of:

- Airborne observation
- Ground/field sensor nodes
- GPS/location information
- Local processing
- Communication
- Data storage
- A base command system
- Two-way command and control

The airborne unit is not the final decision maker. It collects observations, processes basic information, communicates with the base, and executes authorized commands from the base.

---

2. OVERALL SYSTEM IDEA

The complete response system follows this loop:

DISASTER
   ↓
GROUND / AIRBORNE OBSERVATION
   ↓
DATA COLLECTION
   ↓
LOCAL PROCESSING
   ↓
DATA PACKET
   ↓
COMMUNICATION
   ↓
BASE COMMAND SYSTEM
   ↓
SITUATION ASSESSMENT
   ↓
PRIORITY / RESPONSE DECISION
   ↓
COMMAND
   ↓
AIRBORNE / GROUND UNIT
   ↓
NEW OBSERVATION
   ↓
BASE

The key concept is a closed-loop disaster-response information and command system.

---

3. AIRBORNE UNIT — MAIN PURPOSE

The airborne unit should perform five main functions:

A. Observation

Use a camera and selected environmental/motion sensors to observe the environment.

B. Navigation

Determine:

- Latitude
- Longitude
- Altitude
- Time

using GPS/GNSS.

C. Processing

The microcontroller collects sensor data, associates it with position/time, creates structured packets, and manages the unit.

D. Communication

Transmit information to the base and receive commands from the base.

E. Local storage

Store observations when communication is unavailable and transmit them later.

6. GPS/GNSS

A GPS/GNSS module is REQUIRED but is not currently in our hardware inventory.

Use it to provide:

- Latitude
- Longitude
- Altitude
- UTC time
- Position validity/fix status

Preferred interface:

GPS TX → MCU RX
GPS RX ← MCU TX
GPS GND → GND
GPS VCC → regulated supply

GPS is not a disaster sensor.

Its purpose is to answer:

WHERE and WHEN did the observation happen?

Altitude is particularly useful because this is a helium-balloon airborne platform.

For Proteus, if a real GPS model is unavailable, simulate it using a UART/serial data source.

10. COMMUNICATION

The airborne unit requires two-way communication.

Airborne → Base

Transmit:

- Unit ID
- Packet ID
- Time
- GPS position
- Altitude
- Sensor data
- Event information
- Data quality
- Battery status
- System status
- Image ID/reference
- Stored-data information

Base → Airborne

Commands may include:

REQUEST_STATUS
CAPTURE_IMAGE
CAPTURE_SEQUENCE
SEND_STORED_DATA
CHANGE_SAMPLING_RATE
CHANGE_OPERATION_MODE
START_OBSERVATION
STOP_OBSERVATION

The communication link must support both:

DOWNLINK:
AIRBORNE → BASE

UPLINK:
BASE → AIRBORNE

Do NOT assume Wi-Fi is automatically suitable as the final long-range airborne communication system.

For the Proteus prototype, communication may initially be represented by:

MCU ↔ UART ↔ Virtual Terminal

A real radio should later be selected based on:

- Range
- Frequency
- Data rate
- Power consumption
- Antenna
- Regulatory requirements
- Atmospheric operating environment

Clearly identify the radio as TBD/required component if no real radio has yet been selected.

11. DATA STORAGE

Include local storage, preferably a microSD module.

Purpose:

Sensor data
     ↓
MCU
     ↓
microSD
     ↓
temporary storage
     ↓
communication restored
     ↓
transmit missing data

The system must not lose all observations simply because the communication link temporarily fails.

Use packet sequence numbers so the base can identify missing packets.

Example:

LATITUDE      = XX.XXXX
LONGITUDE     = XX.XXXX
ALTITUDE      = XXXX m

TEMPERATURE   = XX.X C

ACCEL_X       = X.XX

EVENT         = FIRE

The packet structure should be modular so disaster-specific payloads can be added later.

Use the available LEDs and buzzer.

Suggested assignment:

15. AUTHENTICATION AND COMMAND VALIDATION

The airborne unit must not blindly execute every received command.

Conceptual process:

Command received
       ↓
Is it addressed to this unit?
       ↓
Is the message valid?
       ↓
Is the command authorized?
       ↓
Execute command
       ↓
Send acknowledgement

For the prototype, implement basic message integrity/authentication.

Do not overcomplicate this with military-grade security unless specifically required.

16. PROTEUS CIRCUIT DESIGN REQUIREMENT

Create the Proteus design in logical sections instead of one confusing schematic.

SECTION 1 — POWER

POWER INPUT
     ↓
REGULATOR
     ↓
3.3V / 5V
     ↓
MCU + sensors + modules

Include:

- Capacitors
- Ground
- Voltage monitoring
- Appropriate protection where practical

SECTION 2 — MCU

Use the appropriate Proteus-supported MCU.

Expose:

- UART
- I²C/SPI
- ADC
- GPIO

SECTION 3 — GPS

GPS UART ↔ MCU UART

Simulate GPS data if necessary.

SECTION 4 — SENSORS

Temperature → MCU ADC/I²C
Light       → MCU ADC
Accelerometer → MCU I²C/SPI
Voltage divider → MCU ADC

SECTION 5 — CAMERA

Represent ESP32-CAM through an appropriate simulated interface if Proteus lacks the actual device model.

SECTION 6 — STORAGE

MCU ↔ SPI ↔ microSD

SECTION 7 — COMMUNICATION

Initially:

MCU ↔ UART ↔ Virtual Terminal

Later replace the simulation interface with the selected real radio.

SECTION 8 — STATUS

MCU → LEDs
MCU → Buzzer

Conceptually:

             TOP / OBSERVATION SIDE

          │      ESP32-CAM        │
          ├───────────────────────┤
          │                       │
          │      MAIN PCB         │
          │   MCU + sensors       │
          │                       │
          ├───────────────────────┤
          │ POWER      STORAGE    │
          │ Battery    microSD    │
          ├───────────────────────┤
          │ COMMUNICATION /       │
          │ RADIO + CONNECTOR     │
          └───────────────────────┘

The camera should have an unobstructed field of view.

The accelerometer should be mounted rigidly to the structure/PCB so its measurements represent platform motion.

Keep power circuitry and sensitive signal circuitry organized to reduce noise.
